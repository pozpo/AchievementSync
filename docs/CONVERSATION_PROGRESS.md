### Earlier: backup upload parallelism throttle and network retry (2026-11-19)

After the user confirmed the previous button fixes were "everything is perfect now", they asked to speed up the actual `Backup saves` upload (they observed ~856 files at ~2–5 s/file). The first implementation parallelised blob creation to 6 in-flight requests via `Parallel.ForEachAsync`; this immediately triggered `HttpRequestException` ("An existing connection was forcibly closed by the remote host", `SocketException 10054`) for the very first blobs being uploaded because GitHub rejected the burst. The code was reverted to safer settings and re-published:

- `CreateBlobAsync` is now wrapped in a retry policy with up to 4 attempts (1 s / 2 s / 4 s / 8 s delays) and a transient-error classifier (`HttpRequestException`, `IOException`, `InvalidOperationException`, `TaskCanceledException`, `TimeoutException`, `SocketException`). When all retries fail, a friendly `GitHubApiException` is thrown instead of the raw HttpRequestException.
- `Phase C` (blob creation) now runs with `MaxDegreeOfParallelism = 2`; the previous 6 saturated GitHub and SH-exceptioned the upload.
- `Phase A` (SHA-256 hashing) runs with `MaxDegreeOfParallelism = 4`.
- Planner's per-file byte load uses `MaxDegreeOfParallelism = 4`. Tree-entry insertion order (and thus the final commit content list order and report order) remains deterministic.
- `PushSaveBackupAsync` powers `BackupProgressPercent` again; the user's two prior successful pushes in the repository tree remain intact (the failed attempt did not finalise its commit).
- Stable executable republished with hash `77C5E864A4AA5DDEBD2BC76E177CC57100932C3E57969302445C52E5B8B34FCF`, 76,578,285 bytes. Functional suite 182/182 pass.

The remaining bottleneck is the literal HTTPS upload speed for ~4–5 MB blobs (Skyrim SE .ess files), which is bounded by the user's upload bandwidth and cannot be accelerated by client code beyond the 2-way concurrency that has now been the safe maximum.
